# 기존 옷장을 Supabase로 옮기는 실행 계획

기준일 2026-10-08. 아래는 앞으로 구현·실행할 순서입니다. 현재 옷 정보 업로드 버튼만으로 사진·생활·수정 이력까지 완전히 이전되지 않습니다.

## 이전 묶음 형식

기존 옷을 등록했던 **원래 브라우저와 주소**에서 내보냅니다. real 데이터만 선택하고 demo/시험 데이터는 제외합니다. 새 Vercel 주소에서는 이전 주소의 IndexedDB를 직접 읽을 수 없습니다.

```text
closet-export-날짜-묶음ID/
  manifest.json           형식 버전, 원본 식별값, 개수, 파일 해시 목록
  wardrobe.json           옷 ID와 전체 속성, 사용자 수정 상태
  preferences.json        생활/지역/초기 설정
  contexts.json           당일 일정
  wear-history.json       착용 선택 기록
  wear-feedback.json      실제 착용 피드백
  legacy-state.json       answers/confirmedGroups 등 보존 상태
  analyses/옷ID.json      등록 당시 분석 기록
  media/옷ID/원본파일
  media/옷ID/제거본파일
```

Blob은 JSON.stringify만 하면 실제 사진을 보존하지 못합니다. 원본 바이트를 별도 파일로 내보내야 합니다. manifest에는 SHA-256(파일 내용이 같은지 확인하는 지문)·바이트 수·형식을 기록합니다. 파일 이름만으로 사진을 합치지 않습니다. 인증 키·로그인 토큰·비밀번호·GPS는 내보내지 않습니다. 이 파일 묶음은 개인 자료이며 GitHub에 올리지 않습니다.

## 실제 실행 단계

| 단계 | 처리 | 완료 조건 |
| --- | --- | --- |
| 1 원본 확인 | PC/휴대폰별 원래 주소·브라우저·real 옷 개수 확인 | 빈 새 주소를 기존 옷장으로 오인하지 않음 |
| 2 백업 | 위 묶음 생성, 원본 브라우저 그대로 유지 | 옷/사진 수, 해시, 사용자 수정값 검증 |
| 3 사전 검사 | ID·필수값·길이·배열·중복·사진 연결·미확인 검사 | 문제 목록을 제시하고 무음 누락 없음 |
| 4 대상 준비 | 적용된 표·RLS·비공개 버킷 확인, 사용자 로그인 연결 | 두 가상 계정으로 소유권 차단 검증 |
| 5 미리보기 | 새로 추가/동일/충돌/미지원 항목 수와 대상 계정 표시 | 어떤 데이터가 바뀌는지 사용자 확인 가능 |
| 6 이전 예약 | import_batches와 import_items에 항목 기록 | 같은 manifest 재실행이 동일 작업으로 인식됨 |
| 7 속성·사진 | 신규 속성/상세 저장, 사진 직접 전송, 완료 해시 확인 | 사진은 uploaded→검증→ready, 미완료는 재시도 가능 |
| 8 생활·기록 | 사용자 설정·일정·착용·피드백·분석 연결 저장 | 원래 옷 ID와 날짜 연결 유지 |
| 9 대조 | 서버에서 다시 읽어 백업과 비교 | 개수뿐 아니라 필드·빈값·해시 일치 |
| 10 새 기기 | 다른 브라우저에서 로그인·사진 열기·가상 추천 | 브라우저 로컬에만 있던 값이 누락되지 않음 |
| 11 전환 | 서버 데이터를 기준으로 읽고 로컬은 캐시/백업으로 유지 | 사용자 확인 후 이전 완료 표시 |

원격 전환 때 모든 기존 사진을 Gemini로 재분석하지 않습니다. 분석 결과와 추정 출처를 그대로 이전합니다. 서버 날씨 캐시는 새로 수집할 수 있으므로 개인 백업에 통째로 넣지 않습니다.

## 값 정리 규칙

- category는 top/bottom/dress/shoe/outer 중 하나인지 확인합니다. 잘못된 값을 임의의 상의로 바꾸지 않습니다.
- 실제 기존 ID를 유지합니다. 허용 형식 밖 ID는 매핑표를 만들고 사진·분석·착용 기록 참조를 함께 변경합니다. 변환 사실을 숨기지 않습니다.
- 0, false, null, 빈 문자열, 필드 없음은 의미를 확인해 보존합니다. ‘일부러 비움’은 수정 표시와 함께 남깁니다.
- 블랙 팬츠→청바지, 후드 재킷→방풍성 확인처럼 추정 정정을 하지 않습니다.
- thicknessSource가 ai_estimate이면 추정 유지, warmth가 null이면 그대로 둡니다. 등록 완료만으로 user_confirmed를 만들지 않습니다.
- 옛 style/bodyNote/달력 관련 값이 발견되면 원본 보존 영역에 남기되 현재 추천에 다시 활성화하지 않습니다.
- 생성 시각을 모르면 과거 촬영일로 채우지 않습니다. 이전 시각과 원래 생성 시각을 구분합니다.
- 생활의 빈 지역 목록과 복수 민감도·느낌을 유지합니다. 새 날짜의 일정은 이전 당일 일정과 구분합니다.

## 충돌과 반복 실행

동일 사용자+옷 ID+내용 해시가 같으면 재사용합니다. 같은 ID인데 내용이 다르면 서버의 revision과 원본을 비교해 충돌로 남깁니다. 현재 upsert의 마지막 요청 우선 처리를 대량 이전에 그대로 쓰지 않습니다.

서로 다른 기기에서 우연히 같은 ID가 다른 옷을 가리키면 별도 옷으로 가져오는 선택과 참조 ID 매핑을 제공합니다. 이름이 같다는 이유로 합치지 않습니다. 실패 항목만 재시도하고 성공 항목은 다시 만들지 않습니다.

사진과 DB는 하나의 트랜잭션으로 묶이지 않으므로 상태를 기록합니다. 실패한 사진은 ready로 표시하지 않습니다. 연결되지 않은 업로드 파일은 해당 이전 작업의 소유권과 참조 여부를 확인한 뒤 정리합니다.

## 되돌리기

이전 묶음이 만든 행/파일과 적용 당시 revision을 기록합니다. 되돌릴 때 이후 사용자가 수정한 행은 삭제하지 않고 충돌로 남깁니다. 기존 서버 옷을 갱신했다면 이전 값 스냅샷으로 복구하며 묶음 전체를 무차별 삭제하지 않습니다. 다른 계정과 다른 작업의 파일은 건드리지 않습니다.

원본 브라우저와 개인 백업은 새 기기의 확인이 끝날 때까지 보존합니다. 저장소 삭제는 자동 후처리로 넣지 않습니다.

## 공동 비용 기록은 별도 이전

실제 로컬 예산 파일은 코드/개인 옷장과 별개입니다. AI 실행을 멈춘 상태에서 사용액·예약액·불확실 호출을 읽고 운영 DB에 한 번만 반영합니다. 이전 고유 키와 합계를 검증한 후 새 서버를 같은 budget_key에 연결합니다. Preview는 별도 시험 예산을 쓰고 Production 원장을 0원으로 다시 만들지 않습니다.

이전 시험은 가상 옷·가상 이미지·Gemini 비활성 상태에서 수행합니다. DB 구조와 접근 제한은 이미 적용했습니다. 개인 사진 전송과 실제 옷장 이전은 아직 수행하지 않았습니다.
