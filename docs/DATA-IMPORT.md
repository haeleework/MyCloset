# 현재 저장·복원 범위와 개인 자료 이전

2026-10-08 · v27. Supabase 수동 전체 저장/가져오기를 구현하고 합성 사진으로 검증했습니다. 사용자의 실제 옷장과 사진은 아직 이전하지 않았습니다.

## 현재 지원

옷ID/속성/화면 상세, 분석 결과와 사용자 수정값, 원본·배경 제거 사진, 생활 설정, 활동 지역, 초기 질문 상태, 일정, 착용 기록, 피드백, 기존 답변과 묶음 확인값을 저장합니다. null/false/0/빈 문자열은 구분합니다. 사진 바이트는 JSON과 분리해 비공개 Storage로 전송합니다. 선택한 촬영 메타데이터에서는 GPS를 제외하지만 원본 사진 바이트의 EXIF를 다시 쓰지는 않습니다.

1. 클라우드 저장 공간 자동 연결 및 현재 revision 확인.
2. 모든 입력과 파일크기·형식 검증. 옷500개, 착용/피드백5000개, JSON3.5MB, 사진20MiB 제한.
3. 예상 revision이 같을 때 데이터 묶음을 저장. 없어진 옷은 논리 삭제하여 과거 참조 보존.
4. 미완료 사진을 전송하고 실제 크기·형식을 확인. 완료 파일은 지문 경로로 재사용. 큰 파일은6MiB 단위로 전송하며 중간 실패 후에는 파일 전체 전송을 다시 시작할 수 있음.
5. 모든 사진 완료를 확인한 뒤 전체 저장 성공 표시.
6. 가져오기는 모든 사진의 SHA256을 검증한 뒤 적용. 이전 로컬 자료는 고유한 백업 키로 보관.

## 기존 개인 자료 이전 시 주의

현재 주소·포트와 다른 브라우저의 IndexedDB를 자동으로 읽지 않습니다. 4335 촬영 자료를4336에 자동 복사하지 않았습니다. 원래 주소에서 저장 기능을 활성화하는 전환은 사용자가 촬영을 마친 뒤 별도로 진행해야 합니다. 데이터가 비어 있는 새 주소에서 저장하면 기존 원격 옷 목록을 바꿀 수 있으므로 UI가 명시적 확인을 요구합니다.

JSON 다운로드만으로 사진 Blob이 보존되지는 않습니다. 범용 ZIP 내보내기/가져오기, 모든 과거 필드 자동 이전, 다른 기기로 동일 데모ID 옮기기는 구현하지 않았습니다. 이미 삭제된 옷ID를 가리키는 과거 착용 기록이 새 계정에 있으면 저장을 거부할 수 있습니다. 이 경우 기록과 옷 참조를 보존하는 별도 이전 작업이 필요하며 조용히 누락하지 않습니다.

의도적으로 지운 과거 기록까지 서버에서 일괄 삭제하는 양방향 동기화는 아닙니다. 같은 날짜의 착용·피드백은 날짜 기반 키로 갱신하고 서버에 이미 있는 다른 날짜의 기록은 유지합니다. 보관/변경 범위는 [데이터 구조](DATA.md)를 따릅니다.

사진 처리 요청의 축소 사본은 옷장 원본을 덮어쓰지 않습니다. 전체 저장 시 원본과 선택한 제거본을 각각 전송합니다. 비용 원장 이전은 서버 운영 단계로만 수행하며 옷장 가져오기로 예산을 초기화하지 않습니다.
